# 企业知识库：业务版本选择与受限计算

本版增强正式问答流水线，保留已有向量检索、PostgreSQL BM25、RRF 融合与重排，不引入新的 Agent 框架、数据库表或调试接口。

## 1. 数据流

入库：文档解析 → 结构化切分 → 提取业务元数据并附到分块 → Embedding → 原有文档/分块记录。

问答：授权范围 → 向量与 BM25 各最多 30 个候选 → RRF 最多 30 个候选 → 补充候选文档业务元数据、排除明确不适用版本 → 重排 → 适用性选择 → 最终最多 8 个片段 → 上下文 → 一次结构化答案生成 → 受限计算复算 → 数字/引用校验 → 回答或拒答。

多轮问答仍先将追问改写为独立问题，再进入同一个 AnswerService，因此也使用本版的适用性和计算逻辑。追问改写仍可能调用模型；本版没有增加新的改写调用或长期记忆模块。

## 2. 业务版本不是入库版本

业务信息存放在 KnowledgeDocument.metadata_json.policy 和 DocumentChunk.metadata_json.policy。没有改动数据库表结构，不需要为本版新建 Alembic 迁移。

| 字段 | 含义 |
| --- | --- |
| document_code | 原文标注的文档编号 |
| business_version | 原文标注的业务版本，如 1.4 |
| effective_from / effective_to | 明确的生效/失效日期，ISO 格式 |
| applicability | 原文标注的适用范围 |
| business_status | 原文标注的现行、归档、废止、草案等状态 |
| topics | 由文档标题提取的有限主题标签，不是完整意图分类 |
| rule_scope / supersedes | 管理员明确维护的规则范围和被替代文档编号列表 |

已有 KnowledgeDocument.version 仍表示入库更新次数；status=ready 仍表示索引可检索。它们都不能代表制度业务版本或业务有效性。复审日期不会自动成为失效日期。

自动抽取仅识别明确标签，例如“生效日期：2026年7月1日”“有效期为2025年1月1日至2026年6月30日”。不根据上传时间、文件序号或相邻文本猜测有效期。日期非法则忽略，前后倒置则保留警告而不据此删证据。

重新入库更新时刷新来源中的业务字段，只保留管理员维护的 rule_scope / supersedes。当前没有新增业务元数据编辑接口或前端管理页；这两个治理字段不是由模型自动决定的。

### 旧索引兼容

查询时只读取本次候选文档前 8 个分块，受租户、可读知识库、文档 ID 和 ready 状态约束。抽取结果留在本次请求内，不写回业务数据库，也不调用文档 Embedding。

所以现有资料无需全量重新生成向量即可使用这项能力；新入库资料会持久化 policy。旧文档若将有效期藏在第 8 块之后，且本次候选也未包含该字段，则无法保证识别，仍视为未知，不擅自排除。

## 3. 如何选择版本和规则

时间选择规则：

- 一个明确日期：按该日期判断适用性，生效/失效日期均包含边界当天。
- 一个明确年份：保留与该整年有交集的版本。年中制度变更不会只留下一个版本。
- 无明确年份日期，但问“当前/现在/现行/最新”：按运行环境的当前日期。
- 多个日期、多个年份或未给时间：不猜测比较/区间意图，不自动过滤为当前版本。
- 元数据缺失：保留候选，交由答案阶段说明不足或冲突。

例如，原文明确历史版本有效期为 2025-01-01 至 2026-06-30，现行版本于 2026-07-01 生效。问 2025 年时排除现行版本；问 2026 年全年时保留两个版本，按时间分段回答。

替代关系仅在同一 rule_scope、明确 supersedes、替代文件有效期覆盖整个查询期间时生效。可跟随明确的替代链；自我替代被忽略，循环关系保留证据以免误删。未知的截止日期不会根据“新文件已上传”自动补齐。

规则范围还增加一个有限的主题优先级：只问 Webhook、且未同时问 API/开放平台时，标题明确为 Webhook 专门规范的候选优先于通用说明。该选择在重排前后都应用，且先于最终 8 条截取；不会直接删除通用文档。比较 API 与 Webhook 时不启用此优先级。

这是有限场景偏好，不是对所有企业制度冲突的自动裁决。部门、员工角色、业务流程等复杂适用条件仍需模型依据原文理解；冲突缺乏明确权威关系时应说明冲突。

## 4. 受限计算

模型输出结构化的计算建议，不输出可执行代码。每个输入包含 source（问题或资料编号）、quote（连续原文摘录）、value（字符串）、unit。计算结果仍必须引用支持它的资料。

程序逐项检查：

1. 引用存在，输入所属资料在该结论的引用中。
2. 摘录确实存在于本次实际上下文或问题，不能把 1100 元截成 100 元、负数去掉负号或截去时刻的秒。
3. 数值、单位与摘录一致；至少一个输入来自知识库，而非全由用户问题提供。
4. 运算属于白名单，满足该运算的约束。
5. 独立复算，与模型建议的 result 一致才允许回答。
6. 计算结论由程序重新生成，不放行附带的未经验证描述；普通事实仍走原有数字、日期和引用检查。

支持的运算：

| 运算 | 支持范围 |
| --- | --- |
| time_add | 起始时刻加正的秒/分钟/小时；整秒累计、不超过 7 天；跨午夜带“第2日”等限定 |
| money_sum | 用户明确要求合计；人民币元金额，用 Decimal 求和 |
| money_difference | 用户明确要求差额；两个人民币元金额，第一个减第二个 |

时间计算采用同一时间基准，不处理跨时区或夏令时。重试绝对时间还要求问题明确无 Retry-After，且忽略请求耗时或每次立即失败；第 N 次投递使用原文默认序列前 N-1 个间隔，不能遗漏、重排，也不能把第 N 次追加重试当作第 N 次投递。

例：18:00:00 起始，加 30 秒、2 分钟、10 分钟、30 分钟、2 小时，得到 20:42:30。这个时刻不要求原文直接出现，因为各项来源和算式已通过校验。

金额输入和建议结果只接受有限十进制、最多 6 位小数、绝对值不超过 10 亿；不自动换汇。为保守处理，含美元、港币等币种标记的来源不用于元金额计算。没有乘除、税率、百分比、工作日、财务审批或任意 Python/SQL 执行功能。

重要边界：算术正确不等于业务公式正确。例如两笔金额究竟能否合计，或某个角色是否适用某项限额，还依赖原文语义与人工评审。这不是通用语义证明器。

## 5. 上下文、接口与过程记录

每个上下文资料块增加“适用性”头部。引用能支持正文和该文档的业务版本/日期属性，但不会因此免除普通事实的数字校验。上下文仍保留总字符预算与每来源最多 4 块限制。相同正文但业务版本/适用性不同的片段不会被当作同一证据去重。

### 正文名额保护（说明片段占位修复）

已确认一个可复现的边界：同一文档的标题、公司名称、元数据、免责声明排在前面时，原有每来源 4 块限制可能截掉后面的规则正文。`evidence_quality.py` 增加保守的内容类型识别，并在最终 8 条截取前和上下文拼接前，优先选择正文，再用剩余名额保留说明信息。

这不是按“有无标题”筛选：未标章节、文档说明章节中的真实规则、包含业务义务的混合元数据均保留正常正文优先级。纯说明资料也不会被删除；明确询问版本号、生效日期、文档编号等属性时，保留原排序。同类片段内部仍保持原来的检索/重排顺序，原有每来源 4 块和总字符预算不变。

这个修复保护已召回的正文，不保证修正所有正文相关性排序错误，也无法恢复已经在 RRF 候选之外的证据。真实请求未保存过程快照时，不能仅凭模型的拒答理由断言它当时看到了哪些片段。

公开 AnswerResult / Citation 格式未改变，前端无需改请求。calculation 仅是内部 AnswerDraft 的结构化字段，不新增公开工具接口。

启用现有 capture_trace / --save-traces 时新增：

- policy_candidates_raw：已授权并补充业务元数据、但尚未做适用性选择的候选。
- policy_candidates：适用期过滤后的候选及 policy_selection 标记，可与上一阶段对比。
- 原有候选、重排、context 记录中的 policy 字段。
- 适用性选择后的候选和 context 中的 evidence_role，标记 content / front_matter。
- calculations：验证成功的操作、输入值标签和结果；失败时记录拒绝原因。

没有保存完整模型推理过程，没有在普通响应中暴露诊断正文，也不记录 JWT 或密钥。只有开启过程记录时才收集这些信息；使用模型评估时仍需现有显式授权开关。

现有关键词评分、题集、参考答案、OCR 流程没有为了本版改分。离线功能测试通过不能代替真实模型准确率，也不能修正扫描文档中的 OCR 错字。

## 6. 使用与验证

本地运行：重启现有 API / Worker Python 进程使新代码生效。如果使用 Docker 镜像部署，在项目根目录执行：

```powershell
docker compose up -d --build api worker
docker compose ps api worker
```

这里只更新应用服务；不要执行删除数据库卷的命令。Compose 的原有启动流程仍会执行已有迁移，但本版未新增迁移。

不调用模型的专项测试：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_policy_selection.py tests/test_calculation_service.py tests/test_answer_service.py tests/test_pgvector_indexing_service.py tests/test_pgvector_document_candidate_indexing.py -p no:locust -o addopts= -q
```

测试包含实际示例语料的历史差旅版本选择；若本地未放置该合成语料则明确跳过该案例。其它测试使用隔离数据库或模拟模型，不修改现有业务数据库。

初版完整非外部集成回归为 420 项通过、22 项外部集成测试被排除。说明片段占位修复增加 17 项回归，最终为 437 项通过、22 项外部集成测试被排除，编译与 git diff --check 通过。新增检查包含真实 TXT 解析、说明片段优先的模拟重排/失败降级、未知正文保留、元数据问答及实际 AnswerService 上下文/引用绑定。未执行真实 PostgreSQL 扩展、模型 API 或付费在线题集验收；需更新容器后才能验证当前部署的真实回答。

真实质量验收沿用 [分层评估说明](../evals/SYSTEM_EVALUATION.md)，先少量测试历史版本、Webhook 401 和时间累加，再运行全题集。真实调用会消耗模型额度。本版实现阶段没有自动执行付费在线评估，也没有宣称整体准确率已提升。

## 7. 代码位置

新增主要模块：

- backend/app/documents/policy_metadata.py：来源业务字段抽取、分块附加、上下文标签。
- backend/app/knowledge/evidence_selection.py：时间范围理解、适用性过滤、明确替代与主题优先级。
- backend/app/knowledge/evidence_quality.py：明确说明片段识别与正文优先级保护。
- backend/app/knowledge/calculation_service.py：输入溯源、白名单计算、受控结果渲染。

接入位置：pgvector_indexing_service.py、vector_repository.py、retrieval_service.py、rerank_retriever.py、context_builder.py、answer_models.py、answer_service.py、answer_validation.py、prompts.py、evaluation/trace.py。
