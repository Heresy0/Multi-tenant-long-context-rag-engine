# 上下文选材、历史规则与多轮评估优化

实施日期：2026-10-05。基于原报告 `20261005T115143156129Z`，本次优先处理“候选已有正确证据，但选材或解释阶段丢失”的问题。

后续报告的两项漏答修复，以及新增的可选本地多轮逐轮诊断，见 [答案完整性修复](ANSWER_COMPLETENESS_FIX.md)。下文保留本轮实施时的验证结果；HTTP多轮缺少完整快照的边界仍成立。

## 1. 改了什么

### 问题感知的上下文选材

新增 `backend/app/knowledge/context_selection.py`，由 `context_builder.py` 在去重、正文优先之后调用。

原流程在同一来源有多个候选时按排名取前4块。XH-031的验收时间证据已进入候选，但计划、会议、账号准备等片段占满了名额，实际签署验收的正文被截掉。

新流程仅在同一来源超过上限时介入：识别问题所问的实际状态/完成时间或原因，给直接支持该问题的正文预留名额，再按原排名填满其余名额。名额允许时仍保留来源的第一条命中；选中片段之间保持原重排顺序。

例如“最后何时验收”优先保留“客户于某日签署最终验收”的证据，而不是拿“原计划某日验收”“客户验收账号完成”证明项目已经验收。明确的“尚未完成”也能成为实际状态证据，不只偏爱肯定句。

边界：这是有界启发式选材，不是事实真实性或文档权威分类器；不能恢复未进入候选的证据，也不能保证理解所有复杂句式。标题/章节包装不能单独当事实，计划性表述不作为实际完成凭据。普通问题和元数据问题不触发此类预留。来源标识增加 `document_id` 回退，避免缺少存储路径时误把不同文档归为一个来源。

预算保持不变：每路检索30条、最终候选8条、每来源最多4块、正文上下文最多12000字符。字符硬上限仍可使预留片段未能装入，诊断会记录这一点，不偷偷扩大预算。

### 历史规则解释

在 `answer_constraints.py` 新增 `temporal_evidence_context()`，使用原有业务时间解析器，把问题期间与资料明确的生效/失效日期相比较，输出覆盖、部分重叠、不重叠、未知或元数据警告，并绑定资料引用编号。

`generation_constraints(question, context)` 和 `prompts.py` 将这些适用关系提供给原有一次结构化生成调用：

- 查询日期不是实际业务日期；不能因为现在是2026年，就把2025年的规则当无效答案。
- 归档状态、“当前标准已变”等提醒，不自动否定当时有效的历史规则。
- 回答历史金额已有直接证据时，不要求额外找到现行替代金额。
- 不同年份的规则不同，不等于资料冲突；冲突判断要限定同一时期、对象和场景。
- 部分覆盖不能概括为全年；未知或异常日期不猜测；复审日期不是失效日期。

没有硬编码公司、题号、550元或650元，也没有把模型拒答强行改成可回答。适用期标签不证明角色、场景或事实已经充分；原有引用校验、必要条件检查、计算校验和未来承诺拒答仍保留。效果需要真实模型复测，不能仅凭提示词修改宣布历史题已通过。

### 具体事件不被通用规范带偏

`evidence_expansion.py` 复用并公开原有事件编号识别函数。`evidence_selection.py` 在检索问题带完整INC事件编号时，不再因为出现“Webhook”一词就额外优先通用Webhook规范。

“是不是Webhook重试引起的，实际根因是什么”需要优先依据具体事件复盘，而不是只引用通用重试规则。普通Webhook规则题仍保留专门规范偏好；这项改动没有取消重排，也没有保证事件复盘一定排名第一。未能保留事件编号的追问改写仍需在线检查。

## 2. 评估标注与诊断

题集版本更新为 `2026-10-05-r5`，由既有生成脚本重新生成：

- XH-MT-03第3轮仍问“之前排队的任务要重提吗？”：核心要求为“不需要”，任务保留与恢复执行作为补充说明；原必要来源不变。未主动解释保留机制不扣核心事实分，但错误宣称任务丢失仍需人工判错。
- XH-D-MT-05第2轮明确为“是Webhook的重试问题吗？实际根因是什么？”：仍要求否定错误归因、说明幂等键问题，并引用事件复盘；没有放宽根因要求。

60道单轮题的问题、评分事实和证据标注均未改，仅标注版本变化。文档语料不变，旧报告不覆盖。改写后的多轮问题必须重新运行；题集摘要变化后不能直接把旧、新整套分数作为同口径基线比较。现有自动评分仍是关键词/来源代理，语义要求需人工复核。

`evaluation/trace.py` 增加两类仅在本地 `capture_trace()` 启用时记录的诊断：

1. `context_selection`：候选数、来源限额后数量、实际装入数量和字符数、预留片段是否成功装入。
2. `answer_decisions`：生成前拒答、生成判定、校验和最终结果，以及引用对应的时间关系。

同时记录文档逻辑ID，便于新快照准确重建来源。不是采集模型隐藏推理，没有新增公共调试接口，正常会话和响应不携带这些诊断。HTTP多轮报告仍不包含完整的每轮片段快照，不能据此宣称多轮证据忠实度已被完整验证。

新增 `scripts/check_context_replay.py`，使用旧授权候选检查新选材策略。它不会重新生成答案或写数据库；问题摘要不一致、候选越权、重复题号或无有效记录都会报错。旧快照缺少来源ID时，按知识库、文档名和规则标签近似分组，结果明确注明这一限制。

## 4. 建议的真实复测

在项目根目录、已激活原虚拟环境及安全设置有效Alice JWT的终端执行。令牌不写入配置、文档或报告。确认 `evals/system_config.local.json` 对应当前授权范围。

先测试历史标准和最终验收两题：

```powershell
$env:REDIS_URL = "redis://127.0.0.1:6379/0"
.venv\Scripts\python.exe scripts/evaluate_system.py --mode live --config evals/system_config.local.json --layers retrieval,rerank,context,answer --case-ids XH-016 XH-031 --allow-model-calls --save-traces
```

再测试时间/角色切换、排队任务和事件根因三组，共9轮：

```powershell
.venv\Scripts\python.exe scripts/evaluate_system.py --mode live --config evals/system_config.local.json --layers conversations --conversation-ids XH-MT-02 XH-MT-03 XH-D-MT-05 --allow-model-calls --allow-conversation-writes
```

这两条会调用真实模型，多轮还会创建临时测试会话并在完成后清理；追问理解可能额外调用模型，不能把9轮等同于9次全部模型请求。报告生成在 `evals/reports/system/<本次时间目录>/report.md` 和 `report.json`；单轮开启快照时还有包含授权正文的 `traces.jsonl`，不要公开上传。

只读重建上下文、不调用模型的检查方式：

```powershell
.venv\Scripts\python.exe scripts/check_context_replay.py --trace-input evals/reports/system/20261005T115143156129Z/traces.jsonl
```

注意：本工具与统一入口的普通 `--mode replay` 不同；后者评分已保存结果，本工具才会用当前ContextBuilder重建选材，但仍不代表新回答实测。
